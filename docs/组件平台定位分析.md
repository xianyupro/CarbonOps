# 组件平台定位分析

> 回答三个问题：组件平台在这套系统里**是什么**、**怎么嵌入**、**往哪演进**。
> 依据：仓库根目录《全流程低碳运行智能监测与调控系统平台需求说明》《需求规格说明书》2.3/2.4/2.5 节，以及当前已实现的四层架构。

---

## 一、定位：一句话

**组件平台是"把元模型和数据组装成可执行调控流程"的运行编排层**——它上承元模型平台（②，能力供给方），下接驾驶舱中心（④，能力消费方），是整个系统从"看得见"走向"调得动"的枢纽。

对照四层架构的职责划分：

```
① 数据基座        提供"原料"（真实工况数据）
② 元模型平台      提供"大脑"（工艺知识 + 四类元模型 = 静态资产）
③ 组件平台   ←    提供"手脚"（把静态资产装配成动态可执行流程）
④ 驾驶舱中心      呈现"结果"（3D 孪生 + 大屏 + 总览）
```

没有 ③，② 的元模型只是一份份"登记在册的文档"；有了 ③，元模型变成**可以被流程调用、产生实时输出、触发报警与调控建议的运行时能力**。

## 二、与需求文档的对应

| 需求条款 | 组件平台的承接方式 |
|---|---|
| 2.4 低代码组态开发"模型控制组件、输入输出绑定" | 控制流编排器的「元模型推理」组件 + 三段式绑定协议 |
| 2.3 模型拖拉拽编排"可视化编排画布、流程配置、调试与发布" | 双语义边画布（控制实线/数据虚线）、运行（仿真）、执行日志 |
| 2.5 场景应用"工序级监测调控" | 工艺工序组件（给料/焙烧挥发/冷却/收尘/排放）按工艺顺序装配即成场景流程 |
| 2.2 数据管理"实时推送" | 数据输入组件（点位读取）直连数据基座 |

## 三、当前实现盘点（截至本轮）

**已有**：
- 声明式组件注册表（20 个组件）：工艺工序 5 + 工件算子 2 + 数据输入 2 + 分析算子 4 + 元模型 1 + 逻辑控制 4 + 输出展示 2
- ApexMotion 式控制流：双语义边、端口=参数、惰性求值、条件/循环、三级容错（简化版）
- 仿真执行引擎：真实读点位、真实分析算子（pandas）、元模型调用计入统计，设备指令只记录不下发
- 编辑器：拖拽装配、正交连线、自动布局、执行回放、小地图

**为什么感觉"四不像"**：因为三个闭环还没闭合——
1. **工艺闭环缺"触发"**：流程目前只能手动点「运行」，没有定时调度/报警触发/数据变化触发的自动执行；
2. **展示闭环缺"绑定"**：流程的输出（调控建议、报警、统计量）还没有反哺到组态画面和驾驶舱（④ 看不到 ③ 算出来的东西）；
3. **模板闭环缺"沉淀"**：工艺工序流程没有固化为"场景模板"（需求 2.5 的挥发窑场景应该= 一条预置流程 + 预置绑定，一键生成）。

## 四、演进路线（建议顺序）

### 第一步：调度触发（让流程"自己跑"）
- 流程工程增加触发器配置：`手动 / 定时(cron) / 报警联动 / 点位阈值触发`
- 后端加一个轻量调度器（APScheduler），到点自动 run 并落 FlowRun
- 价值：③ 从"演示工具"变成"持续运行的监测调控引擎"——这是需求 2.5 的核心语义

### 第二步：输出反哺（让④看见③）
- 「调控建议」「触发报警」组件的输出写入驾驶舱告警流（已部分实现：output.alarm 直写 alarms 表）
- 流程运行统计进驾驶舱中心（今日执行次数/成功率/平均耗时）
- 大屏增加「流程运行状态」组件

### 第三步：场景模板化（让场景=流程）
- 把"五段工艺流程"固化为挥发窑场景的默认模板，场景创建向导（需求 2.5）直接实例化流程并预绑定数据基座点位
- 行业场景页（④ 组内）从静态卡片变成流程实例的入口

### 第四步：组态联动（远期）
- 组态开发（studio）的组件可绑定控制流节点的输出引脚（如把「调控建议」组件的输出显示到组态画面），实现"流程驱动画面"

## 五、一句话回答"嵌入方式"

> 数据基座给数据 → 元模型给算法 → **组件平台把两者装配成持续运行的工艺流程** → 流程的输出和状态最终呈现在驾驶舱中心。组件平台不是又一个"画流程图的 demo"，而是整个系统唯一让"模型 + 数据 + 规则"真正**运行起来**的地方——它的成熟度直接决定平台是"监测系统"还是"监测与**调控**系统"。
